# Backend plan: SQL Server + C# REST API (side project to the UX)

Status: **Phases 1 to 7 built.** Written 2026-10-29. Each phase ends with a commit (when asked) and a stop, so you can `/clear` and start the next one with "Start Phase N of docs/backend-plan.md".

## 1. Decisions (answered 2026-10-29)

| Topic | Decision |
| --- | --- |
| Database | SQL Server (T-SQL). Plain `.sql` provisioning script that **you run by hand**. |
| Data access | **Dapper** with hand-written SQL. No EF Core, no migrations. The script is the schema source of truth. |
| Service | .NET 9 C# REST API in `/server`, Swagger (OpenAPI) enabled, JWT bearer auth. |
| Auth | Email or account number plus password. Short-lived access token plus a rotating refresh token stored hashed. Passwords hashed with PBKDF2 or Argon2. No external sign-in. A user profile has a **10-digit account reference number** (Princess style). |
| Still mocked | The AI concierge, live ship telemetry and weather, and payments (card charging; stored card last four digits and receipts are real data). |
| Reference data | Seeded by separate scripts, outside the schema script. |
| User data | Seeded by separate persona scripts: a strong set of people in partial-completion states across the whole journey, so UAT never starts from scratch. |
| Offline | Not a goal. Every non-mocked data call is async REST. The backend is assumed always available. The mocks are **removed**, not kept behind a flag. |
| Connection string | You give it to me after the provisioning script is done (after Phase 4). |

## 2. Assumptions I am making (tell me if wrong, ideally before Phase 1)

1. **Data shape.** Core entities (users, bookings, guests, payments, orders, reservations, tickets and so on) are proper relational tables with foreign keys. Deeply nested, UI-shaped payloads (check-in step records, health answers, packing lists, customs declarations, advisor replies) are stored as `NVARCHAR(MAX)` JSON columns with `CHECK (ISJSON(...) = 1)`. This keeps the schema tractable. Say so if you want those fully normalised.
2. **The demo clock and scenarios.** The UI today has a demo clock ("jump to a stage") and 16 failure and risk scenarios (`src/domain/scenarios.ts`). A real server needs a notion of "now" for persona testing. My default: a `DemoState` table per user holding a clock offset and the active scenarios, applied by the API only when the user is flagged `IsDemo`. Real users get real time. The scenario *fault rules* (forced errors) stay client-side.
3. **Personas become users.** The 12 existing personas (gerald, maria, linda, alexander, the Harpers, the Brennans) become seeded users with a shared demo password, plus extra personas for the pre-booking and post-travel states (section 5). Children get supervised accounts (no password, managed by the booker).
4. **Login identifier.** The 10-digit account number is unique per user profile, generated by the server, and works as the username alongside email.
5. **Money** is stored as integer cents (`BIGINT`), as the UI does. Times are stored as UTC `DATETIME2(0)`; ship-local times are derived from the itinerary and zones in the reference data.
6. **Tests.** Most of the existing `*.test.ts` files exercise the mock implementations. When a mock is removed its tests either move to the pure domain logic they really cover, or are deleted with the mock. Pure `src/domain` logic and its tests stay.
7. **Tooling.** `dotnet` is **not installed** in this WSL environment. Install the .NET 9 SDK before Phase 5 (`! sudo apt-get install -y dotnet-sdk-9.0`, or Microsoft's install script). Phases 1 to 4 need no SDK. The CLAUDE.md rule against browser testing still applies; backend checks are `dotnet build`, `dotnet test`, plus the existing npm checks for the frontend.
8. **Pricing and booking rules** (fares, promotions, cancel terms, price protection, loyalty discounts) live today in `src/domain`. The server must be the authority for them, so those rules are **ported to C#** and covered by tests that mirror the TypeScript tests. The TypeScript copies stay only where the UI needs them for display.

## 4. Data model overview (detail comes in Phase 1)

- **Reference (read-mostly):** `Ships`, `Decks`, `CabinCategories`, `Cabins`, `Ports`, `Sailings`, `ItineraryDays`, `Venues`, `Menus`, `MenuItems`, `Excursions`, `Events` (programme), `Shows`, `Fares`, `Promotions`, `Packages`, `AddOns`, `PhotoCatalogue`, `Crew`, `Faqs`, `ContentBlocks`, `MusterStations`.
- **Booking:** `Bookings`, `BookingGuests`, `BookingDrafts`, `Payments` (receipts), `SavedCards` (brand, last four, expiry only), `Acceptances`, `Cancellations`, `PastTrips`, `Loyalty`, `FutureCruiseCredits`.
- **Pre-cruise:** `TourBookings`, `TourCartLines`, `DiningReservations`, `Purchases` (packages and add-ons), `ChecklistTicks`, `PackingTicks`, `TravelPlans`, `AssistanceRequests`, `Waitlists`, `Queues`, `ShowTickets`, `AdvisorRequests`, `UpgradeBids`, `ClubRegistrations`, `Medallions`, `BagTags`, `PrepTicks`, `Marketing consents`.
- **Check-in and boarding:** `CheckinRecords` (per guest, JSON step data), `CheckinPayments`, `ArrivalPlans`, `BoardingPasses`, `EmbarkProgress`.
- **On board:** `MusterConfirmations`, `PlanEvents` (my programme), `Orders` and `OrderLines`, `Messages` (travel-party chat), `ServiceThreads` and `ServiceMessages`, `ChatBlocks`, `ChatReports`, `FamilyZones`, `KidClubCheckins`, `HealthReports`, `HealthRequests`, `RoomSettings`, `PhotoSelections`, `PhotoPurchases`, `LaundryRequests`, `WifiDevices`, `Budgets`, `UpdateAcks`, `ServiceRequests`, `DrinkLogs`, `TopUps`, `Gratuity`, `Parties` and `PartyInvites`, `GameProgress`, `TvState`, `Reports`, `Feedback`, `Folio` lines.
- **After the cruise:** `DisembarkChoices`, `Customs`, `OnwardPlans`, `NightChecklist`, `FinalBill`, `Cases`, `PostFeedback`, `Referrals`, `RebookHolds`, `DeskAppointments`.

Cross-cutting conventions: surrogate `UNIQUEIDENTIFIER` or `BIGINT` ids (decided in Phase 1), `CreatedAt` and `UpdatedAt` columns, `RowVersion` on rows that are edited concurrently, soft delete only where the UI shows deleted state, every user-owned row carries `BookingId` or `UserId` so authorisation checks are one join.

## 5. Persona seed scenarios (to be finalised in Phase 4)

Each scenario is a set of users plus data in a partial state. Journey stages follow `STAGE_IDS` (booked, preCruise, checkIn, embarkation, seaDay, cozumel, belize, roatan, seaDay2, farewell, disembark, postCruise) plus **pre-booking** (no booking yet, a saved draft, favourites).

- **Existing 12 personas**, each seeded at a different stage so every stage has coverage.
- **Pre-booking:** a brand-new account with nothing; a returning guest with a saved draft and favourites; a guest comparing sailings with a Captain's Circle tier and future cruise credit.
- **Booking in progress:** a draft with partial guest details; a booking confirmed with deposit only (balance due soon); a booking with a payment problem.
- **Pre-travel:** documents missing or passport problems; excursions in the cart and booked; dining reserved; packages bought with a price-drop credit owed; check-in not yet open, open and half done, done.
- **Travel-agent booking** (documents handled by the agent).
- **Party types:** solo traveller; couple; family with young children; family with teens (supervised accounts); friends sharing a chat but in separate cabins; multigenerational group with a helper; honeymoon or occasion booking.
- **Special needs:** mobility and tender assistance, hearing, vision, CPAP or oxygen, service animal, severe allergy, vegan or halal or kosher.
- **On board:** each port day, a sea day, the all-aboard countdown, a tender day, an illness notice, a late order, a missing child, a slow chat.
- **Post-travel:** walk-off option chosen; customs done or not; final bill with a disputed line; open case; feedback given or not; rebook hold; loyalty tier change.
- **Edge cases:** cancelled booking, changed sailing, a declined payment, a supervised child account, a revoked helper.

Seed scripts are idempotent (re-runnable) and offer a "reset persona data" script that restores the starting state without touching reference data.

### Phase 6. API: account, trips, payments, documents, notifications, support, privacy (built)
- Maps to `account`, `trips`, `payments`, `documents`, `notifications`, `support`, `help`, `privacy`, `budget`, `aboard.feedback`, `saved` and `discover.favourites` (33 routes, data model section 6.1). Ports the name-change, document requirement, payment state, check-in window, notification, retention, consent and budget rules to `server/Princess.Api/Domain`.
- Adds the demo-aware clock (`IUserClock`, D4): a user flagged `IsDemo` gets real time plus `demo.DemoState.ClockOffsetSeconds`, everyone else real time. `GET /bookings/{n}` returns the booking core (the old `bookings.get`) and `GET /sailings` is public.
- Deliberate differences from the mock, all stricter: a profile or document is changed only by the person, the booker of the booking (for anyone on it), a supervised child's booker, or a helper holding the permission; a child's budget limit is set by that child's booker; outsiders always get `notFound`. Card charging for `payBalance` (`POST /bookings/{n}/payments/balance`, one saved card) is recorded as captured; Phase 7 adds `IPaymentGateway` and idempotency keys on the new booking routes, and the frontend phase for payments should move to `POST /bookings/{n}/pay-balance`.

As in Phase 5, none of the Dapper SQL has touched SQL Server; the smoke calls in `server/README.md` are the check.

### Phase 7. API: discover and booking (built)
- Maps to `discover` and `booking` (18 routes, data model section 6.2): `sailings/offers|bookable|{id}/quote|rooms|cabins` (public), `booking/fares|quote`, `me/booking-prefill`, `me/draft` (get, save, discard, resume link), `POST /bookings`, `bookings/{n}/detail|pay-balance|change|cancel`. Pricing, fares, promotions, pay plan, payment parts and the bank check, cancel terms, change check, Captain's Circle discount and future cruise credit, draft cleaning and the step rules, and the sample staterooms are ported to `server/Princess.Api/Domain` (`Pricing.cs`, `PolicyRules.cs`, `DraftRules.cs`, `CabinRules.cs`), with tests mirroring `booking.test.ts` and `discover.test.ts`.
- `IPaymentGateway` (`Services/PaymentGateway.cs`) holds the pretend bank: a card ending 0002 is `declined`; a card that is not the default, or any card payment of $3,000 or more, needs the code 123456 (`challenge` `required` / `wrong`); a device wallet never does. It throws before any money moves, and a payment row is written only after it returns. Booking is idempotent per draft id, and `book` and `pay-balance` also take an optional `Idempotency-Key` header (8 to 80 of letters, digits and `_ . : -`); a repeat returns the first result without charging, and another person's key is `409 idempotencyKey`.
- Deliberate differences from the mock: the draft id is chosen by the server (random, 32 hex characters) and comes back from `PUT /me/draft`, because it is the secret in the resume link; the booker is guest 1 of the booking and the other guests are kept as guest details (they have no accounts); `GET .../cabins` also drops staterooms already booked; change and cancel are for the booker only; the booking's contact address (street, city and so on) is not stored, because `dbo.Bookings` keeps only the email and phone, so `contact` comes back with those two filled in. `dbo.QuoteLocks` is not written yet: prices are fixed, so the `priceChanged` check recomputes the total and compares it with `expectedTotal`.
- Interior fares by sailing and the room type multipliers have no table in the schema, so they are constants in `Pricing.cs` (sailings, dates and open or closed still come from `ref.Sailings`). The sample staterooms use the same formula as `ref.Cabins`.
- **Verify:** `dotnet build`, `dotnet test` (337 tests: ported rules, then the HTTP pipeline for discover, the funnel, booking, charging, idempotency, pay balance, change and cancel, and an OpenAPI coverage check). As before, none of the Dapper SQL (`DapperBookingStore`) has touched SQL Server; the smoke calls in `server/README.md` are the check.

## 7. Risks and things to watch

- **Size.** The API has roughly 200 methods across about 40 groups. The plan splits them by journey stage so each phase is reviewable.
- **Business rules in two languages.** Porting pricing and policy to C# creates two copies. Mitigation: the server is the authority, and ported tests mirror the TypeScript ones; the UI keeps only display-side copies.
- **Clock and scenarios.** Section 2, item 2 is the biggest design question. Settle it in Phase 1.
- **No SQL Server or `dotnet` here.** SQL cannot be executed by me; you run scripts and report errors. C# can be compiled once the SDK is installed.
- **Secrets.** Connection string, signing key and demo passwords stay out of git (user-secrets, environment variables, and a `.gitignore` check in Phase 5).
- **Public endpoints.** Pass lookup by booking number and last name needs rate limiting and uniform `notFound` responses to avoid enumeration.
